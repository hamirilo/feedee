# Feedee v2 要件定義書

> 策定日：2026-07-02

---

## 1. プロダクトビジョン

**RSSリーダーとブックマーク管理を対等に統合した、個人向け情報収集・整理ツール。**

どちらか一方に偏っているツールが多い中で、RSS・あとで読む・ブックマークをシームレスに連携させる点が差別化ポイント。

---

## 2. ターゲットユーザー

- **メインターゲット：** 自分（オーナー）
- **将来想定：** 拡張する可能性あり（マルチユーザー対応は設計から考慮する）
- **ホスティング形態：** セルフホスト前提（デプロイ先は未定）

---

## 3. コア機能要件

### 3-1. 情報フローの設計（最重要）

情報は以下の3層で流れる。

```
[RSS / URL入力 / ブックマークレット]
           ↓
    ① あとで読む（Inbox）
       読んだら消化。残すなら ↓
           ↓
    ② そのうち読む（Someday）
       今じゃないけどいつか。残すなら ↓
           ↓
    ③ ブックマーク（永久保存）
```

#### あとで読む（Inbox）
- RSS記事・URL直接入力・ブックマークレットから追加（初期実装）
- 将来：ブラウザ拡張・スマホ共有・外部サービス連携
- 読んだら既読として消化（自動）
- 残したい場合は「そのうち読む」に移動、またはブックマーク昇格

#### そのうち読む（Someday）
- 「あとで読む」の第2段階
- 今すぐ読まないが、いつか読みたいコンテンツを保留

#### ブックマーク（2種類を明確に分ける）

| 種別 | イメージ | 用途 |
|------|----------|------|
| **リソース型** | アイコン配布サイト・ツール集 | 必要な時に参照するURL |
| **コンテンツ型** | コラム・記事 | 内容が良くて記憶に残したいもの |

> 現状の問題：この2種類が同列に並んでいるため、整理が困難。v2では明確に分離する。

---

### 3-2. RSSフィード管理

- フィードはシステム全体で1つ（URL単位で重複なし）
- **購読はユーザーごとに管理**（カテゴリ・表示名・並び順はユーザー固有）
- 同じURLを複数ユーザーが購読してもフェッチは1回（効率化）
- どのフィードを購読しているかは他ユーザーに非公開

### 3-3. 記事管理

- 記事状態（既読・お気に入り・あとで読む移行）はユーザーごとに管理
- 検索・フィルタ・ソート・ページネーション
- 表示モード切り替え（リスト・コンパクト・カード）

### 3-4. ブックマーク管理

- タグ付け（Bookmarkのみ、複数付与可）
- カテゴリ分類（フラット。階層なし）
- 状態管理（ピン留め・お気に入り・あとで読む）

---

## 4. 分類・整理の設計

### カテゴリ

- **フラット構造**（階層なし）
- フィード・ブックマーク共通で使用
- 1アイテムに1カテゴリ
- 色付き

### タグ

- **Bookmarkのみ**に付与可能
- 複数付与可
- 横断的なラベルとして使用

## 5. 技術スタック（確定）

```
┌─────────────────────────────┐
│         Next.js             │  フロントエンド（App Router）
│    フロントエンド全般         │  UX最大化を優先
└──────────────┬──────────────┘
               │ HTTP API
┌──────────────▼──────────────┐
│          FastAPI             │  メインAPIサーバー（Python）
│  認証・CRUD・AI機能           │  ORM：SQLAlchemy + Alembic
│  ブックマーク・あとで読む等   │  Swagger自動ドキュメント
└──────────────┬──────────────┘
               │ 内部API呼び出し
┌──────────────▼──────────────┐
│         Go Worker            │  RSSフェッチワーカー（既存拡張）
│  定期フェッチ・記事取り込み   │  高並行・軽量・現状資産活用
│  全文抽出                    │
└──────────────┬──────────────┘
               │
┌──────────────▼──────────────┐
│         PostgreSQL           │  共有DB（両サービスが参照）
└─────────────────────────────┘
```

### 技術選定の理由

| 技術 | 選定理由 |
|------|----------|
| **Next.js** | UX最大化。エコシステム・UIコンポーネント資産が豊富 |
| **FastAPI** | ORM・Pydantic・AI統合が強力。自動ドキュメント。AIエージェントとの相性◎ |
| **Go Worker** | 現状資産を活用。並行RSSフェッチに最適 |
| **PostgreSQL** | 本番DB。FastAPIとGoから共有 |

> **Djangoテンプレートは廃止。** FastAPIがAPIサーバー専念。GoワーカーはAPIの向き先をDjango→FastAPIに変更するのみ。

## 6. 認証

- **JWT（アクセストークン＋リフレッシュトークン）**

- 将来のモバイルアプリ・ブラウザ拡張にも流用可能

## 7. 実装優先順位

### Phase 1：DB設計（最初に固める）

今回の要件を反映した新スキーマ設計。

主要テーブル候補：

```
User
Feed（URL単位・グローバル）
Subscription（ユーザー×Feed・購読管理）
Article（Feed取得記事）
ArticleUserState（ユーザーごとの記事状態）
ReadingItem（あとで読む）
SomedayItem（そのうち読む）
Bookmark（リソース型 / コンテンツ型）
BookmarkUserState
Category（フラット・フィード/ブックマーク共通）
Tag（Bookmarkのみ）
```

### Phase 2：FastAPI基盤

- プロジェクト構成・Docker Compose
- PostgreSQL接続・Alembicマイグレーション
- JWT認証API（登録・ログイン・リフレッシュ）

### Phase 3：コアAPI

1. あとで読む（ReadingItem / SomedayItem）CRUD
2. Feed・Subscription・Article CRUD
3. GoワーカーのAPI向き先をFastAPIに変更
4. Bookmark CRUD（2種類）

### Phase 4：Next.jsフロントエンド

APIが動いてから画面を構築。

1. 認証フロー（ログイン・ログアウト）
2. あとで読む画面
3. フィード・記事一覧
4. ブックマーク（リソース型・コンテンツ型）
